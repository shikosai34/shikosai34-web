## 2.2 想定利用者

- **一般来場者**（地域住民・近隣校の生徒とその保護者）
  - 主な利用目的: 開催日時、アクセス、企画内容の確認
  - 主な利用環境: スマートフォン
- **在校生・受験検討者**
  - 主な利用目的: タイムテーブル、企画詳細の確認
  - 主な利用環境: スマートフォン
- **出展団体**（サークル・クラス）
  - 主な利用目的: 自団体の掲載内容の確認
  - 主な利用環境: スマートフォン／PC
- **協賛企業**
  - 主な利用目的: 自社ロゴの掲載確認
  - 主な利用環境: PC

**スマートフォンでの閲覧を第一の設計基準とする。** 利用者の多くを占める一般来場者・在校生がスマートフォンで閲覧するため。Figma のアートボード作成もモバイル幅から着手する。PC 版はモバイル版を基準に展開し、PC 画面で生じる余白は背景の表現で埋める。

- **テーマ**: 守破離
- **デザインキーワード**: 和風 × サイバーパンク
- **ページ構成（URL一覧）**: 17件。第2.7節

## 2.4 技術スタック

第33回リポジトリの構成をそのまま採用する。新規に技術選定を行わない理由は、前年度の実装を参照できること、および学習コストを抑えて内容の制作に時間を配分できることによる。

- **Bun**（ランタイム／パッケージ管理）: 依存関係の管理、ユニットテストの実行
- **proto**（バージョン管理・ツールチェーン）: Bun 等のバージョン統一
- **Astro**（フレームワーク）: 静的サイト生成
- **Tailwind CSS**（CSS）: デザイントークンによるスタイル定義
- **Biome**（Linter / Formatter）: コード品質の統一
- **lefthook**（Git フック）: コミット前のチェック実行
- **Cloudflare Workers**（ホスティング、Wrangler 経由）: 本番配信 ［確定］

**ホスティングの構成 ［確定］:** **Cloudflare Workers を用い、Wrangler 経由でデプロイする。** 過去回のページと同じ構成であり、第4.5節の「Workers が稼働する限り公開を継続する」はこの構成を指す。Cloudflare Pages は採用しない。

この決定により次が定まる。

- デプロイの設定を `wrangler.toml` に記述する
- 過去回のページと同じ配信基盤上に置くため、公開終了後の扱い（第4.5節）を過去回と揃えられる
- **FesFlow 側は Cloudflare Pages を用いる構想であり、HP とは別のプロダクトになる。** 同一の Cloudflare アカウント上で両者を運用するため、ドメインの割り当てを調整する（第1.5節の C-02）

**開発環境:** `proto` による Bun のバージョン統一を、開発者間の環境差を吸収する手段とする。

**参考:** FesFlow 側は Cloudflare Pages / Cloudflare Tunnel、API は Hono で構築する構想である（システム構想記事より）。

## 2.5 HP と FesFlow の役割分担

茨香祭のデジタル基盤は次の2つで構成される。

- **HP（本プロジェクト）**
  - 役割: 開催情報・出展情報の**閲覧**
  - 性質: 静的サイト。ログイン不要、個人情報を収集しない
- **FesFlow**
  - 役割: 購入・体験に関わる**取引**
  - 性質: 動的システム。来場者のマイページ、サークル向けPOS

**原則: HP は取引に関わる機能を実装しない。該当する機能は FesFlow へリンクする。**

**FesFlow への誘導 ［確定］:** トップページには FesFlow 全体への導線を置き、FesFlow 導入サークルの `/circle/[slug]` には該当サークルの FesFlow ページへの導線を置く。いずれも外部の別システムへ遷移することが分かる文言・見た目にする。具体的なリンク先 URL は FesFlow 側との調整事項（C-01）とする。

### `/` トップページ

トップページには、端末時刻を基準にした「現在実施中のステージ企画」と「次のステージ企画」を掲載する ［確定］。これは当日の実際の進行状況を反映するものではないため、**「リアルタイム」ではなく「予定時刻に基づく表示」**と明記する。

| 項目 | 内容 |
| --- | --- |
| 判定に使う時刻 | 閲覧端末の時計 |
| 判定に使うデータ | タイムテーブルの企画ごとの開始日時・終了日時 |
| 表示内容 | 現在実施中の企画、次に開始する企画、開始・終了予定時刻、タイムテーブルへの導線 |
| 実装 | 静的サイトのため、クライアント側 JavaScript で表示を切り替える |
| 制約 | 端末の時計と予定時刻に基づく表示であり、当日の遅延・中止・順番変更には追従しない |

タイムテーブルの各企画には、タイムゾーンを含む正確な開始日時・終了日時を必須項目として持たせる ［確定］。時刻だけでは日をまたぐ判定や開催日ごとの表示を正しく行えないためである。

**JavaScript が動作しない場合の表示は ［要検討］:** 「予定時刻に基づく表示は利用できません」と表示して `/timetable` への導線のみを出すか、タイムテーブルの先頭の企画を固定表示するかを決める。どちらを採るかにより、トップページの初期表示とアクセシビリティの設計が変わる。

### 2.8.1 `/circle` サークル一覧

| 項目 | 内容 |
| --- | --- |
| 表示項目 | 団体名、サムネイル画像、カテゴリ、実施場所 |
| 絞り込み | カテゴリによる絞り込み |
| 分類方法 | **出展主体による分類** ［確定］ |

**分類方法 ［確定］:** カテゴリは次の3区分とする。出展の内容ではなく**出展主体**で分ける。

| カテゴリ | 対象 |
| --- | --- |
| クラス | 学級単位の出展 |
| 部・同好会 | 部活動および同好会の出展 |
| 有志サークル | 上記に属さない有志団体の出展 |

区分が少なく、各団体が自団体の該当先を迷わずに選べる。**この3区分を原稿収集フォームの選択肢（第2.9.3節「カテゴリ」）にそのまま用いる。** 分類を後から変えると収集済みの回答を割り当て直す作業が発生するため、**フォーム配布より前にこの区分を確定させる。**

**［要検討］の論点:**

1. **1団体が複数カテゴリに該当する場合の扱い。** 出展主体による分類のため、原則として1団体は1区分に定まる。ただし「クラスと有志サークルの合同出展」のような例が生じうるため、その場合の扱い（いずれか一方を選ばせるか、複数選択を許すか）を決める。単一選択と複数選択では、フォームの入力形式・スキーマの型（文字列か配列か）・絞り込みの実装が変わる。
2. **団体数と一覧の表示方法。** 出展団体の総数が ［未確認］ である。数十件を超える場合、1ページに全件を並べるとモバイルでの縦スクロールが長くなる。件数が判明した時点で、カテゴリごとの見出し分割を行うかを判断する。

### 2.8.2 `/circle/[slug]` サークル詳細

**この画面が HP と FesFlow の接続点であり、設計上もっとも検討を要する。**

| 項目 | 掲載 | 備考 |
| --- | --- | --- |
| 団体名 | する | |
| 紹介文 | する | アレルギーに関する記述が必要な場合はここに含める |
| 画像 | する | 枚数の上限は ［未定］ |
| 実施場所 | する | マーキング付きの会場マップを掲載する。場所を機械的に特定する教室 ID または座標を使用する |
| 実施時間 | する | |
| カテゴリ | する | |
| SNSリンク | する | 任意項目 |
| **FesFlow へのリンク** | する | **FesFlow 導入サークルのみ** |
| メニュー | しない | FesFlow 側で表示 |
| 価格 | しない | 掲載可否に食い違いがあり ［要確認］。第2.6節の「メニュー価格」と同一の論点であり、あわせて決定する |
| レビュー | しない | FesFlow 側で表示 |
| 待ち時間 | しない | FesFlow 側で表示 |

#### slug の値について

Issue のコメントに「Slug はそれぞれのサークル名が入り」とある。サークル名をそのまま slug に用いる場合、日本語を含む URL となる。次の問題が生じる。

- URL がパーセントエンコードされ、`/circle/%E3%81%82...` のような文字列になる。SNS で共有した際に判読できない。
- 団体名に記号（`&`、`/`、空白など）が含まれる場合、URL として使用できず個別の変換規則が必要になる。
- 団体名が変更された場合、URL が変わり既存のリンクが無効になる。

**代案:** サークルごとに英数字の識別子（例: `/circle/robot-club`、または連番 `/circle/a01`）を設定し、ページ内に日本語の団体名を表示する。識別子は原稿収集フォームで各団体に入力してもらうか、実行委員会側で採番する。**この点は Figma のデザイン作成前に決定する必要がある**（URL がページ設計に影響するため）。

#### FesFlow 未導入サークルの表示

FesFlow の導入は全サークル一律ではない（レビュー機能が「FesFlow 導入サークルのみ可能」とされているため）。したがって `/circle/[slug]` には次の2つの状態が存在する。

| 状態 | 表示 |
| --- | --- |
| FesFlow 導入 | FesFlow へのリンクを表示する |
| FesFlow 未導入 | リンク領域を表示しない、または「当日は現地でのお受け取りとなります」等の代替文言を表示する |

**Figma では両方の状態をデザインする必要がある。** 片方のみを作成すると実装時に判断が必要になる。

### 2.8.3 `/event` `/event/[slug]` ステージ企画

Issue の確認事項「`/event` と `/circle` の関係」に対する回答は「event はステージ企画を想定」である。したがって次のとおり整理する ［確定］。

| 対象 | 掲載先 |
| --- | --- |
| 常設の出展（模擬店、展示、体験など） | `/circle` |
| ステージ上で時間を区切って実施する企画（演奏、パフォーマンス、競技など） | `/event` |

**［要検討］** 同一の団体がサークル出展とステージ出演の両方を行う場合、`/circle/[slug]` と `/event/[slug]` の相互リンクを設けるかを決める。

### 2.8.4 `/timetable` タイムテーブル

| 項目 | 内容 |
| --- | --- |
| 表示軸 | 日付（2日間）× 会場 × 時刻 |
| 表示形式（PC） | 縦軸を時刻、横軸を会場とする表形式 |
| 表示形式（モバイル） | 会場ごとに切り替える縦一列のリスト形式 |
| 掲載情報 | 開始時刻、終了時刻、企画名、実施団体、会場 |

**留意点:** 直前の変更が発生しやすい情報である。第2.9節の手順に従い、開催直前にも更新できる体制を確保する。

### `/band/[slug]` バンド詳細

ステージ企画のうちバンド出演を扱う個別ページとして作成する ［確定］。`/event/[slug]` から該当するバンド詳細へリンクするかは、ステージ企画とバンドのデータの対応方法とあわせて決める ［要検討］。

| 項目 | 掲載 |
| --- | --- |
| バンドのサークルカット | する |
| バンド紹介 | する |
| 楽曲紹介 | する。曲名、原曲アーティスト、演奏順を掲載する |

**楽曲の公開タイミングは ［要検討］:** 開催前に全曲を公開するか、開催直前・当日以降に公開するかを、出演者との調整を含めて決める。決定により、楽曲データの公開日とページ上の非表示状態が変わる。

### 2.8.5 `/map` 会場マップ

| 項目 | 内容 |
| --- | --- |
| 掲載情報 | 校内の建物・教室の配置、各サークルの出展場所、ステージ位置、トイレ・救護室・喫煙所などの設備 |
| 形式 | 2D 地図。画像1枚、SVG による領域指定、または階層別の複数画像のいずれかは ［要検討］ |
| 3D 地図 | 採用しない |
| サークルとの連携 | 各サークル詳細ページにマーキング付きの地図情報を掲載する |

**留意点:** モバイルでの閲覧が中心となるため、画像1枚を縮小表示すると判読できない。拡大表示の手段（ピンチ操作の許容、階層別の分割表示）を設計時に決める。3D 地図は作成・掲載しない。

**［要検討］の論点:** 2D 地図の形式を、画像1枚・階層別の複数画像・SVG による領域指定のいずれにするか決める。サークル詳細ページには、選択した形式に応じて該当場所をマーキングした地図を掲載する。

| 形式 | 実装の難易度 | 必要な作業 | サークル詳細でのマーキング |
| --- | --- | --- | --- |
| 画像1枚（PNG / WebP） | 低 | 画像を配置し、`alt` と補足テキストを添える | サークルごとにマーキング済み画像を用意すれば可能 |
| 階層別の複数画像 | 低〜中 | 階層数だけ画像を用意し、切り替えの操作を実装する | サークルごとに該当階層のマーキング済み画像を用意すれば可能 |
| SVG による領域指定 | **高** | 下記のとおり | できる。サークル詳細では該当領域を強調表示する |

**SVG を採用する場合に必要となる作業:**

- **図版を SVG で作成する。** 元の配置図がラスタ画像（写真、スキャン、PowerPoint からの書き出しなど）である場合、SVG へのトレースが必要になる。デザイン作業として相応の時間を要する。
- **各出展場所を個別の要素として持たせる。** 教室ごとに `<path>` / `<a>` を分け、サークルの識別子（第2.8.2節の slug）と対応づける。この対応表は出展場所が確定してからでないと作れず、**直前の場所変更のたびに SVG の書き換えが発生する。**
- **アクセシビリティ対応。** リンクを持つ図形にはキーボード操作とフォーカス表示、および読み上げ用のラベルが必要になる（第4.1節）。単なる画像であれば `alt` とテキスト併記で足りる。
**サークル詳細ページのマーキング方法 ［要検討］:** 次のいずれかを採用する。いずれの場合も、出展場所を機械的に特定する項目（教室 ID または座標）をサークルのデータモデルに持たせる。

1. SVG で領域を指定し、該当サークルの領域を強調表示する。
2. サークルごとにマーキング済みの画像を用意する。

**［未確認］** 校内配置図の元データがどの形式で存在するか（SVG / Illustrator 等のベクタ形式か、画像か、紙のみか）。ベクタ形式が既にあれば SVG の難易度は下がり、紙のみであれば作図から始まるため画像1枚の採用が現実的になる。

## 2.9 コンテンツの管理方法

**データモデルは YAML を基本とする。** 静的サイトで扱うデータは YAML でリポジトリ管理し、Astro Content Collections で読み込む。スキーマ（Zod）の定義は変更しない。お知らせについては microCMS の導入を検討するため、microCMS で管理する範囲（お知らせコレクション）は Astro Content Collections の対象外とする。

### 2.9.1 コレクションの構成

`src/content/` 以下に、コンテンツ種別ごとのコレクションを置く。

- `circles` — サークル情報。YAML（静的・リポジトリ管理）
- `events` — ステージ企画情報。YAML
- `bands` — バンド情報・楽曲情報。YAML
- `timetable` — タイムテーブル。YAML
- `sponsors` — 協賛企業情報。YAML
- `staff` — 実行委員情報。YAML
- `goods` — グッズ情報。YAML（販売がある場合のみ作成）
- `faq` — 質問・回答。YAML（掲載内容決定後に作成）

`news` は microCMS での管理を検討する対象とする ［要検討］。導入する場合は `src/content/` のコレクションには置かない。導入の可否と、導入しない場合の管理方法を決める。

各コレクションには `src/content.config.ts` でスキーマ（Zod）を定義し、必須項目の欠落や型の誤りをビルド時に検出する。`/about`、`/theme`、`/access`、`/cautions` のように単一ページで内容が固定されるものは、コレクションとせずページ内に直接記述する。

**YAML の整形方法は ［要検討］ とする。** Biome は YAML の整形に対応しないため、YAML 用の別ツールを導入するか、整形対象外としてレビューで確認するかを決める。

### 2.9.2 更新の手順

1. 対象の YAML ファイルを編集する（サークル、企画、タイムテーブル等の静的データ）。
2. `docs/<内容>` ブランチで Pull Request を作成する。
3. レビュー承認後に `main` へマージする。
4. Cloudflare へ自動デプロイされる。

**公開日の扱い:** お知らせなど公開日を持つコンテンツには `publishedAt` を必須項目とし、並び順に用いる。将来の日付を指定した項目をビルド時に除外するかは実装時に決める。

### 2.9.3 原稿の反映

サークル情報は静的データとしてリポジトリで管理する。Google フォームで各団体から収集した回答は、確認を経てから手作業で YAML へ反映する。フォームの回答をそのまま公開すると、誤字や不適切な記述、画像形式の不統一がそのまま反映されるため、掲載内容の確認を挟む。あわせて、紹介文に個人名・連絡先が含まれないことを確認する（第4.4節）。

**収集する項目:** `circles` コレクションのスキーマは次を前提とする。**下表は各団体がフォームで入力する項目のみを示す。** 実行委員会が後から付与する項目は次項に分けて記述する。

| 項目 | 必須 | 備考 |
| --- | --- | --- |
| 団体名 | 必須 | |
| 団体名（かな） | 必須 | 並び順に使用 |
| URL識別子 | 必須 | 第2.8.2節の slug。英数字とハイフンのみ |
| 紹介文 | 必須 | 文字数の上限を指定する |
| カテゴリ | 必須 | 選択式 |
| 実施場所 | 必須 | 教室 ID または座標を含め、地図上の場所を機械的に特定できるようにする |
| 実施時間 | 必須 | |
| FesFlow 導入予定 | 必須 | リンク表示の判定に使用 |
| 画像 | **任意** | 縦横比・解像度・形式を指定して提出させる |
| SNSリンク | 任意 | |

**画像が任意であることの影響:** 画像のないサークルが存在するため、一覧・詳細の両方で代替表示が必要になる（第3.7.1節の `Image/Placeholder`）。また提出形式を指定しないと縦横比が揃わず、加工作業が発生する。

#### 実行委員会が後から付与する項目

**次の項目は原稿収集フォームでは集めず、情報部が後から追記する。** 各団体には値が分からない項目であり、また収集の時点では確定していないためである。

| 項目 | 付与する時期 | 付与する主体 | 備考 |
| --- | --- | --- | --- |
| **FesFlow のリンク先URL** | FesFlow 側でサークルのページが用意された後 | 情報部 | 第2.8.2節の「FesFlow へのリンク」。フォームの「FesFlow 導入予定」は各団体の申告であり、実際のURLとは別の項目である |
| 画像のファイル名 | 提出画像を確認・加工し、リポジトリへ配置した後 | 情報部 | フォームでは画像そのものを受け取るため、`src/` 以下のパスは収集時点で存在しない |
| 掲載順（並び順を手動で指定する場合） | 全団体の情報が揃った後 | 情報部 | 並び順を自動で定める場合は不要 |

**スキーマ設計への影響:** これらの項目は**収集直後には値が存在しない**。したがって `src/content.config.ts` では次のいずれかとする。

- **省略可能な項目として定義する**（Zod の `.optional()`）。値がない状態でもビルドが通る
- 必須としたうえで、収集時に暫定値を入れる。ただし暫定値のまま公開される危険がある

**方針: 省略可能な項目として定義し、値の有無で表示を切り替える。** FesFlow のリンクは第2.8.2節のとおり導入・未導入で2状態あり、**「URL が未設定」と「FesFlow を導入しない」は、表示上はいずれもリンクを出さない状態になる。** ただしこの2つを同じ扱いにすると、URL の設定漏れに気づけない。**「FesFlow 導入予定」が真であるにもかかわらず URL が未設定の項目を、公開前に一覧して確認する。**

**［要検討］** 上記の確認を、ビルド時のスキーマ検証で機械的に行うか（導入予定が真ならURLを必須とする条件付き検証）、公開前の目視確認に留めるかを決める。団体数が多い場合は前者が確実である。

## 2.10 機能要件一覧

画面上の動作を伴う機能を列挙する。**Figma では第3.7.2節のとおり、動作前後の両方の状態を作成する。**

| # | 機能 | 内容 |
| --- | --- | --- |
| F-01 | ページ間ナビゲーション | ヘッダーのハンバーガーメニューに17ページを一覧で表示する。階層構造は設けない ［確定］ |
| F-02 | ハンバーガーメニュー | 全画面幅で開閉でき、全ページを一覧として提示する |
| F-03 | FesFlow への遷移 | トップページから FesFlow 全体へ、`/circle/[slug]` から該当サークルへ誘導する。導入・未導入の2状態に対応する |
| F-04 | サークルのカテゴリ絞り込み | `/circle` での絞り込み |
| F-05 | タイムテーブルの日付切り替え | 1日目／2日目の切り替え |
| F-06 | 地図の埋め込み | `/access` に Google Maps。読み込みは遅延させる |
| F-07 | 会場マップの拡大表示 | `/map` での拡大操作 |
| F-08 | OGP 画像の出力 | ページごとの OGP 設定 |
| F-09 | サイトマップ生成 | `@astrojs/sitemap` を利用 |
| F-10 | 予定時刻に基づくステージ表示 | トップページで端末時刻とタイムテーブルの開始・終了日時から、現在・次のステージ企画をクライアント側 JavaScript で表示する |

**方針:** 静的サイトとして構築し、サーバー側の処理を必要とする機能（フォーム送信、ログイン、動的な検索）は実装しない。該当する機能は FesFlow または外部サービスへ誘導する。**サイト内検索は実施しない**（17ページ規模では必要性が低い）。

**ナビゲーションの方針 ［確定］:** ページはハンバーガーメニューにまとめる。メニュー内に親子の階層構造は設けず、全ページを同じ階層の一覧として提示する。PC 版もこの情報構造を引き継ぐ。
